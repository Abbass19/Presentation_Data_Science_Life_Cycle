The example · HCAT Insight

The problem

  • A cardiac hospital collects patient complaints, in Arabic.
  • For each one, an officer assigns nine labels from the HCAT taxonomy (Healthcare Complaints Analysis Tool). It is slow and not always consistent.
  • Goal: the model suggests the labels, a person confirms them.
Complaint text (Arabic)

Only the modelling side is covered here — no software architecture.
The example · data

What the data looked like

  • Arabic (standard + dialect) with English medical terms
  • Patient text: avg ~330 characters, up to ~1,450
  • Two hospital texts: avg ~155 and ~140 characters
  • Real labels from officers; nobody measured inter-annotator agreement
  • Split: 380 train / 96 test (random, same for every model)

Number of records

111 before I started · ~500 when the job began · 476 after cleaning. The 1,816 is a published study on English GP complaints, for context.

The example · the prediction problem

Not one problem, but nine targets

From the patient text

  • Domain (3 classes)
  • Category (7)
  • Sub-category (26)
  • Fine-grained label (78 Arabic / 73 English)

From the hospital texts

  • Severity (3, ordered)
  • Stage of care (6)
  • Harm (5, ordered)
  • Improvement-opportunity type (3: ordinary, red flag, never event)

First plan: nine independent classifiers. Hold that thought.

(A tenth label, Status, was constant and was dropped — the easiest model we ever built.)

The example · constraints

The environment removed most options early

What this ruled out

  • cloud APIs (no internet, hospital IT policy)
  • fine-tuning large models (no GPU)
  • running a large local model (limited RAM)
  • deep models trained from scratch (380 training records)

RAM and latency numbers in our docs are estimates, not measurements. RAM was roughly “8 GB or less”.

The example · a common question

“Why not just use an LLM?”

In our situation

  • No internet, so no API
  • Data stays inside the hospital network
  • CPU only, limited RAM (even a bigger Whisper model was hard to load)
  • Retraining has to stay cheap

If those limits did not exist

  • A zero-shot LLM would be a reasonable first baseline
  • Fine-tuning an Arabic BERT on a GPU
  • Explanations and summaries become possible
  • We would still evaluate on our own data and keep a human in the loop

So: it did not fit the environment — we never measured how it would have done.

The first plan

Plan v1 and how we would judge it

Models

  • Sentence embeddings stored in a database
  • A: one logistic regression per target
  • B: two multi-head models (one per text)
  • Idea: a shared model could use correlations between labels

Evaluation

  • Target: about 0.8 accuracy (“acceptable, not outstanding”)
  • Macro-F1 and per-class results
  • One random 80/20 split, same for all models
  • A published GPT-4o study as a rough reference

Not in the plan: cross-validation, a separate validation set, a “always predict the biggest class” baseline. More on that near the end.

The first approach was not enough

What do you do when the target is missed?

Options we listed

  • merge rare labels
  • generate more data (paraphrase, translation, LLM)
  • collect more real data
  • look for an LLM-based approach
  • ship anyway, with a human reviewing

What we agreed with the supervisor

  • keep going with the ML models as they are
  • retrain as data grows (at roughly 1.5×, 2×, 2.5× the data)
  • try existing NER and speech models
  • leave the “launch now?” question open

A reframing that helped: every target is basically its own small project, with its own problem and its own failure modes.

Revising the plan

At some point we noticed the labels are not independent

  • Category with the Domain prediction added as input: 63.4% / macro-F1 0.485, versus 60.2% / 0.448 for the flat model.
  • Small gain, no significance test — but it hinted at a structure.
  • Multi-head networks share an encoder, yet each head ignores the others.

Annotators effectively work in an order: Domain → Category → Sub-category → Severity → Stage → Harm.

Revising the plan

Plan v2: what to test, and what to set aside

To test

  • Logistic regression as the baseline
  • Stacked models (earlier predictions as features)
  • XGBoost with extra features
  • Ordinal logistic regression for Severity
  • Better embeddings (multilingual MPNet)

Considered, not pursued

  • Parallel multi-head networks — ignore label dependency, heavy on CPU
  • Bayesian networks — hard to estimate with ~500 records
  • CRFs — a lot of machinery for this data size

Only considered; never built.

Revising the plan

Then we noticed it is a tree

  • Each Domain only has certain Categories; each Category only certain Sub-categories.
  • So: one model per branch (1 + 3 + 7 = 11).

Category macro-F1

The Management branch is an easier two-class problem (Environment vs Institutional Processes); always predicting the larger class gives roughly 64%.

Revising the plan

Some targets were not practical with this data

  • 78 / 73-class labels: macro-F1 ≈ 0.15 (flat), 0.12 (stacked), 0.14 (final run).
  • ≈ 6 records per class; ≈ 50 per class would need ≈ 4,000 records.
  • Architecture changes did not help — they cannot create data.
  • So these labels stay manual; synthetic data was discussed but not tried.

The same point, smaller

Several sub-category branches had 3–6 test records. A score on 4 records says very little.

Summary

What the example showed about Model Planning

  • The environment narrowed the options before any experiment did.
  • A plan should say how results will be judged — baselines, metrics, validation — not only which models.
  • Understanding the structure of the targets helped more than switching algorithms.
  • Accuracy can be misleading when one class dominates; look at the small classes.
  • The best model on paper is not always the one that fits the situation.
  • Plan → build → look at the results → revise the plan.

Questions? Happy to go into any part of it.

Appendix A3

A note on the F1 numbers

  • Documentation says macro-F1 is the main metric, but in the Feb 2026 report recall equals accuracy in every row — which is what weighted averaging gives.
  • Severity (ordinal): per-class F1 = 0.85 / 0 / 0 → macro ≈ 0.28; weighted ≈ 0.63, close to the reported 0.62–0.64.
  • Harm binary: per-class F1 = 0.97 / 0 → macro ≈ 0.49; weighted ≈ 0.91, close to the reported 0.90.
  • Stage ≈ 0.25 is macro (per-class: 0.22, 0.40, 0.64, 0, 0).
  • So tiers in that report mix two kinds of average. Recomputed from the per-class tables; the raw report file was not available.
Appendix A4

Stage: the concept-score maths

  • For each concept m: embed a list of example sentences, average them, normalise → unit vector u_m.
  • For each complaint: up to 6 sentences, each embedded → s_j.
  • Score: f_m = max_j ( s_j · u_m ).
  • ≈ 15 scores → logistic regression → Stage.
  • Notes from the project: normalise embeddings first; build concept vectors from full sentences rather than keyword bags.
  • Concepts include: arrival, administration, bed/room, billing, cleanliness, clinical delay, communication/scheduling, conflicting diagnosis, discharge disagreement, doctor follow-up, food, lab/imaging, location, clinical errors, staff behaviour.
